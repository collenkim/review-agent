# 검증 범위 정책 (예시 템플릿)

> `--policy`로 넘기는 문서의 예시입니다. 그대로 쓰지 말고 프로젝트에 맞게 고쳐서 쓰세요.
> 이 내용은 모든 dimension(convention/requirement/blast-radius/test-coverage)과
> verify 단계에 공통으로 주입되어, **무엇을 지적하고 무엇을 지적하지 않을지**를 정합니다.

## 지적 대상

- diff에서 **추가·변경된 줄**에서 발생한 문제
- 변경으로 인해 diff 밖에서 깨지게 된 부분 (호출부 미수정 등)

## 지적 대상 아님

- diff에 포함되지 않은, 원래부터 있던 코드의 문제 (이번 변경과 무관하면 언급하지 않는다)
- 포매터·린터가 자동으로 잡는 항목 (들여쓰기, 줄바꿈, import 정렬, 세미콜론 등)
- 개인 취향 수준의 스타일 선호 (규칙 문서에 명시되지 않은 것)
- 동작에 영향 없는 리네임·주석 오타
- 생성된 코드, 벤더 디렉토리, 마이그레이션 스크립트

## 심각도 기준

| 심각도 | 기준 |
|---|---|
| `high` | 동작이 틀리거나, 데이터가 깨지거나, 보안 문제가 되는 경우. **머지를 막아야 하는 수준** |
| `medium` | 규칙 위반이 명확하고 고쳐야 하지만 당장 장애로 이어지지는 않는 경우 |
| `low` | 개선하면 좋은 수준. 리뷰어가 무시해도 되는 정도 |

## 보고 기준

- 확신이 없으면 지적하지 않는다. 근거를 diff에서 짚을 수 없으면 보고하지 않는다.
- 같은 원인에서 나온 여러 위치는 하나로 묶어 보고한다.
- 규칙 문서에 없는 내용을 임의 기준으로 지적하지 않는다.

## 테스트 요구 수준

> `--test-coverage`를 쓸 때만 의미가 있습니다.

- 새로 추가된 **public 메서드·API 엔드포인트**에는 테스트를 요구한다.
- 분기(조건문)가 추가된 로직에는 정상/예외 케이스 테스트를 요구한다.
- 다음은 테스트를 요구하지 않는다: 설정 파일, DTO·엔티티의 단순 필드 추가, 로그 문구 변경, 문서 수정
